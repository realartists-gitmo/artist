Everything is a file. The same read(), edit(), write() tools that interact with OS filesystem state also interact with all other noun states. oh my pi pioneered this idea, creating URI namespaces like repo://xxxx/pr/1 as a general resolution surface for all the various bullshit connected to forge interaction tools and clis. This finding scales up. agents:// has the live or dead append-only logs of the agents, etc.
The verb space is extremely constrained. read(), edit(), write(), bash(), abort(), poll(), send(), find(), grep(), eval() (probably a python REPL). These all speak the language of the filesystem. For simplicity's sake, tools are radically non-modal---there is no fire-and-forget single bash configuration---bash spawns a live terminal session that you can send into. Creation does not automatically return read data.
Self-modifiability and iteration is first-class, but not to a wasteful level. Making the entire harness an image the agent can inspect is bulky and stupid. The core of the harness kernel does not need to be inspectable. But a huge amount of subsystems traditionally considered core do need to be pluggable through a WASM extensability surface---the 'tools' we ship will be compiled tools in tools://. The model can look in, edit tools, write new tools, read current tools, and the trusted harness kernel will hot compile the wasm extensions and load them. Same with everything else that doesn't have a justification for stability.
Every system in the harness can call its own tools. Bash can call harness tools. The python REPL has them as built-in functions, etc. This makes it programmable. This rule needs to be fundamental by construction---there needs to be a single unified API that bash and the REPL just grab, rather than novel implementations of this idea for each surface.
Files are sometimes 'sessions.' Sessions are things that have active, live, updating state. abort(), send(), and poll() are deliberately designed for the session shape. Another agent with a growing transcript is a session. A bash window is a session. A python REPL is a session.
Things background by default. This encourages parallelism.

ALL TOOLS must be batching-native without introducing modality or multiple different tools. Needs to happen with this movement.

One KEY primitive about files. Files have lines. But normal line-number addressing for edit tools is bad, and string patch addressing is also bad. For that reason, we have a Rust crate called 'teca' that can take in exactly the line text and CST information we want to validate and invalidate anchor addresses, and have durable anchors. This should be our primitive replacement for line numbers proper, which should exist nowhere.

Every noun is a resource. All resources are addressed by URIs. Some resources are normal OS files and fall out of the filesystem. Some are actually files, but our resource handler wants to represent them being somewhere else in addition to their filesystem location. For example skills are just files, and to load a skill is just to read it. But skills in the global directory need to be flatted with skills that are project local, so they need a minted novel namespace called skills:// that sauces out the URIs.
Tools interact with resources in a way that abstracts over all of the diverse backend complexity. So the resource router needs to figure out what to do with read(repo://xxx/pr/1)---namely, it needs to figure out that this operation actually needs to call the github API and return the PR data, then represent it in the file shape. Same with everything else.
Resource handling and routing should also probably be self-modifiable and extensible, but im unsure how to do this. Maybe a resources:// dir?
